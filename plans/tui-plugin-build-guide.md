# Plan: Building a TuiPlugin for OpenCode

> **Status:** Draft plan. No code changes proposed — this documents the
> working pattern derived from the published `@sstreichan/opencode-tps@0.1.5`
> artifact and is intended as a reference for building future TuiPlugins.

## Why this is not the generic "OpenCode plugin" guide

The published plugin-build guide (`viking://.../opencode-plugin-build-guide`)
describes **hook-based plugins** (`Plugin` type from `@opencode-ai/plugin`).
That pattern uses esbuild + tsc with full bundling.

**TuiPlugin is a different export type** (`TuiPlugin` from
`@opencode-ai/plugin/tui`). It registers TUI components into OpenCode's
Solid.js render tree via `api.slots.register(...)`. The framework deps
(`@opentui/solid`, `@opentui/core`, `solid-js`) are **peerDependencies** and
**must stay external** — bundling duplicates Solid.js and breaks reactivity.

The guide's "single self-contained ESM file" promise cannot be honored by a
TuiPlugin. The correct tool is **`tsc` with `jsx: "preserve"`**, not esbuild.

## Worked example: `@sstreichan/opencode-tps@0.1.5`

The installed artifact in
`~/.cache/opencode/packages/@sstreichan/opencode-tps@latest/node_modules/@sstreichan/opencode-tps/`
is the canonical reference build:

```
dist/
├── tps.js              ← entry: 27 lines, wires state, exports default { id, tui }
├── tps.d.ts            ← entry declarations
└── src/                ← modular pieces, generated by tsc
    ├── cleanup.js   / .d.ts
    ├── constants.js / .d.ts
    ├── hooks.js     / .d.ts
    ├── sampling.js  / .d.ts
    ├── session.js   / .d.ts
    ├── slots.js     / .d.ts
    ├── tps-calc.js  / .d.ts
    └── types.js     / .d.ts
```

Key observations:

- **Pure `tsc` build** — no esbuild, no bundler.
- **JSX preserved as runtime calls** — output uses
  `import { jsx as _jsx, jsxs as _jsxs } from "@opentui/solid/jsx-runtime"`.
  tsc with `jsx: "preserve"` does NOT transpile JSX; the host's JSX runtime
  does. This is what allows peer deps to stay external.
- **Default export preserved** — `export default { id: "...", tui }` is the
  `TuiPluginSpec` shape that OpenCode's loader expects.
- **`.d.ts` generated** — tsc with `--declaration`.
- **`peerDependencies` only** — no framework deps in `dependencies`.

## File layout

```
my-tui-plugin/
├── src/
│   ├── index.ts          ← entry: tui function, default export
│   ├── constants.ts      ← magic numbers
│   ├── types.ts          ← interfaces
│   ├── tps-calc.ts       ← pure calc functions (or domain logic)
│   ├── sampling.ts       ← (plugin-specific) state-buffer helpers
│   ├── session.ts        ← (plugin-specific) metadata helpers
│   ├── hooks.ts          ← OpenCode event subscribers, returns dispose fn
│   ├── slots.ts          ← api.slots.register({ order, slots })
│   └── cleanup.ts        ← dispose aggregator
├── dist/                 ← generated, not committed
├── package.json
└── tsconfig.json
```

**Module split rationale** (from v0.1.5):

| Module | Purpose | Pure? |
|---|---|---|
| `constants.ts` | All magic numbers (windows, thresholds) | yes |
| `types.ts` | Interfaces, type-only | yes |
| `tps-calc.ts` | Pure calculations, no side effects | yes |
| `sampling.ts` | Mutable buffer helpers (push, prune, clear) | side-effectful |
| `session.ts` | Async metadata fetches, in-memory cache | side-effectful |
| `hooks.ts` | `setupHooks(state)` → `dispose()`; subscribes events | side-effectful |
| `slots.ts` | `registerSlots(state)`; TUI components | side-effectful |
| `cleanup.ts` | `disposeAll(state)`; clears intervals, maps, sets | side-effectful |
| `index.ts` | Entry; builds `state`, wires everything, default export | side-effectful |

Pure modules are trivially testable. Side-effectful modules take a `state`
object, never module-level singletons (those leak across plugin instances).

## State pattern

```ts
// src/index.ts (v0.1.5 style)
import { createSignal } from "solid-js"
import { setupHooks } from "./hooks"
import { registerSlots } from "./slots"
import { disposeAll } from "./cleanup"
import type { TuiPlugin } from "@opencode-ai/plugin/tui"

const tui: TuiPlugin = async (api, _options, _meta) => {
  const state = {
    streamSamples: new Map(),
    messageStats: new Map(),
    sessionMeta: new Map(),
    lastKnownTps: new Map(),
    completedSessions: new Set(),
    api,
    version: createSignal(0),
    tick: createSignal(0),
    metaVersion: createSignal(0),
  }

  const disposeHooks = setupHooks(state)
  registerSlots(state)

  api.lifecycle.onDispose(() => {
    disposeHooks()
    disposeAll(state)
  })
}

export default {
  id: "my-tui-plugin",
  tui,
}
```

**Critical:** all mutable state lives on the `state` object. No
module-level `let`/`const` for plugin state. This is what allows the plugin
to be loaded multiple times (project-local + global, or multiple instances)
without state collisions.

## `tsconfig.json`

```json
{
  "compilerOptions": {
    "target": "ES2022",
    "module": "ESNext",
    "moduleResolution": "Bundler",
    "lib": ["ES2022", "DOM"],
    "jsx": "preserve",
    "jsxImportSource": "@opentui/solid",
    "declaration": true,
    "outDir": "dist",
    "rootDir": ".",
    "strict": true,
    "esModuleInterop": true,
    "skipLibCheck": true,
    "isolatedModules": true
  },
  "include": ["src/**/*"]
}
```

Key choices:

- **`jsx: "preserve"`** — do NOT transpile JSX. The host's
  `@opentui/solid/jsx-runtime` handles it. This is what makes
  peer-dep-external JSX work.
- **`jsxImportSource: "@opentui/solid"`** — matches the `/** @jsxImportSource */`
  pragma in source files and tsc's emitted `import` from
  `@opentui/solid/jsx-runtime`.
- **`module: "ESNext"` + `moduleResolution: "Bundler"`** — modern ESM
  resolution that doesn't require `.js` extensions in import specifiers.
- **`rootDir: "."`** (not `"src"`) — required so `dist/src/*.js` is emitted
  alongside `dist/<entry>.js`. If you set `rootDir: "src"`, tsc flattens
  everything to `dist/*.js` and loses the module structure.
- **`outDir: "dist"`** — the published artifact dir.

## `package.json`

```json
{
  "name": "@scope/my-tui-plugin",
  "version": "0.1.0",
  "type": "module",
  "main": "dist/index.js",
  "exports": {
    "./tui": "./dist/index.js"
  },
  "files": [
    "dist/",
    "README.md",
    "LICENSE"
  ],
  "engines": {
    "opencode": ">=1.3.14"
  },
  "peerDependencies": {
    "@opencode-ai/plugin": "*",
    "@opentui/core": "*",
    "@opentui/solid": "*",
    "solid-js": "*"
  },
  "devDependencies": {
    "@opencode-ai/plugin": "*",
    "@opentui/core": "*",
    "@opentui/solid": "*",
    "solid-js": "*",
    "typescript": "^5.x"
  },
  "scripts": {
    "build": "tsc",
    "test": "vitest run",
    "prepublishOnly": "npm run build"
  }
}
```

Notes:

- **`peerDependencies` is mandatory** for the framework deps. Consumers
  (OpenCode) provide them. If you move them to `dependencies`, npm may
  install duplicate copies and break reactivity.
- **`devDependencies` mirrors the peer deps** so `tsc` can type-check and
  emit declarations that import from those packages.
- **`files: ["dist/"]`** — ships only the built output. `src/` is excluded.
- **`prepublishOnly: "npm run build"`** — guards against publishing a stale
  `dist/`.
- **No esbuild, no Bun** — `tsc` is sufficient.

## Build & verify

```bash
npm run build
ls -la dist/                       # expect: <entry>.js, <entry>.d.ts, src/*.js, src/*.d.ts
ls dist/src/                       # expect: 8 .js + 8 .d.ts files for the modular layout

# Confirm JSX stayed as runtime calls (not transpiled to h() etc.):
head -3 dist/slots.js              # expect: import { jsx as _jsx } from "@opentui/solid/jsx-runtime"

# Confirm peer deps are NOT bundled (they should be bare imports):
grep -rE 'from "(solid-js|@opentui|@opencode-ai)' dist/ | head -5
# expect: lines like `from "solid-js"` (bare specifier, host resolves)
```

## Load test

```bash
# Back up first
cp ~/.config/opencode/opencode.json{,.bak}

# Add the plugin (edit config; the `opencode plugin` CLI is for installs, not manual config)
# Add: "@scope/my-tui-plugin@0.1.0" to the "plugin" array

opencode run --print-logs --log-level DEBUG "respond with the word 'pong'"
# Look for: message="Plugin initialized"
```

If you want a marker-file proof (per the generic guide), add a 3-line block
at the top of the `tui` function:

```ts
import { appendFileSync } from "node:fs"
const MARKER = "/tmp/my-tui-plugin-loaded.log"
try { appendFileSync(MARKER, `[${new Date().toISOString()}] loaded\n`) } catch {}
```

Then:

```bash
rm -f /tmp/my-tui-plugin-loaded.log
opencode run --print-logs --log-level DEBUG "ping"
cat /tmp/my-tui-plugin-loaded.log   # expect: one line with current timestamp
```

## Why this is different from the generic guide (recap)

| Aspect | Hook Plugin (generic guide) | TuiPlugin (this plan) |
|---|---|---|
| Export type | `Plugin` (named or default) | `TuiPluginSpec` default `{ id, tui }` |
| Bundler | esbuild (full bundle) | none — tsc only |
| Framework deps | bundled | external (peerDependencies) |
| JSX handling | n/a (no JSX in hook plugins) | `jsx: "preserve"` → runtime JSX |
| Output | single self-contained `dist/index.js` | `dist/<entry>.js` + `dist/src/*.js` |
| Why external deps | n/a | must share host's Solid.js runtime |

## Local source vs published artifact

The reference example above documents the v0.1.5 *published* artifact
(the modular tsc build installed via `npm install
@sstreichan/opencode-tps`). The **local source** in this repo is
intentionally a different shape:

| Aspect | Published v0.1.5 (cache) | Local source (this repo) |
|---|---|---|
| Entry file | `dist/tps.js` (27 lines, modular) | `tps.tsx` (447 lines, monolith) |
| Module layout | `dist/src/*.js` (8 modules) | none — single file |
| Build | `tsc` → `dist/` | none — ships raw `.tsx` |
| `package.json` `exports` | `{ "./tui": "./dist/tps.js" }` | `{ "./tui": "./tps.tsx" }` |
| `package.json` `files` | `["dist/", "README.md", "LICENSE"]` | `["tps.tsx", "README.md", "LICENSE"]` |
| `package.json` scripts | `build` / `test` / `prepublishOnly` | none |
| `devDependencies` | `typescript` + `vitest` | none |

Both files claim `version: "0.1.5"`, but they are distinct artifacts. A
`git clone` + `npm publish` from this repo would publish the raw `.tsx`
shipment, not the modular `dist/` documented above. The local source is
the "reverted" state per the user-confirmed decision below.

## Local operations (Makefile)

The local repo uses a `Makefile` for version bumping and publishing —
distinct from the published v0.1.5's `npm scripts`:

```makefile
make check     # bracket-balance sanity check on tps.tsx
make version   # bumps version = <last-tag-minor>.<git-rev-count>
make publish   # version + npm publish
make clean     # rm -rf node_modules bun.lock
make ls
```

`make version` reads the last git tag, takes `MAJOR.MINOR` from it, and
appends the commit count: `v0.1.X` where `X = git rev-list --count HEAD`.
This auto-versioning was the subject of the reverted `176792e` /
`59fcce8` / `bdef7fd` / `6796820` / `b77de9b` / `3214722` / `741ef56` /
`9f299da` / `18fbe36` / `d74fedb` / `5128646` / `0d7e373` / `6710a3d`
chain, but the `Makefile` itself survived the revert and is the current
operational entry point.

## Decisions and open questions

### Resolved (user-confirmed 2026-06-16)

1. **Re-apply modularization to local source: NO.**
   Current `tps.tsx` (447-line monolith, raw `.tsx` ship) is the canonical
   state for this repo. Do not attempt re-modularization.

2. **Modular attempt did not work** (reason recorded at `bd39ecf` →
   reverted at `5fefbab`). The reverted commit also added (and removed):
   `AGENTS.md` (125 lines), `Makefile` (31 lines — re-added by the
   revert and still present), `opencode.json` (34 lines), `package-lock.json`
   (5260 lines), `test/{sampling,session,tps-calc}.test.ts` (393 lines
   of vitest tests), and `tsconfig.json` (19 lines). Specific failure
   mode not yet captured. The published v0.1.5 IS the modular artifact,
   but the user-side experience was negative. Treat modularization as a
   known-failed approach **for this specific plugin**; the pattern may
   still work for new TuiPlugins with different shapes.

3. **JSX vs no-JSX: resolved (use JSX).** The published v0.1.5 uses JSX
   (`@opentui/solid/jsx-runtime` in `slots.js`); the current local source
   uses JSX (`<For>`, `<Show>`, `createMemo`). The intermediate "remove
   solid-js deps" attempt at `5ab88fe` (revert at `9d29948`) shows the
   trade-off was explored and the no-JSX path was abandoned.
   **Resolution: use JSX** (matches current local source and the
   published artifact).

4. **`opencode plugin list` behavior: user error, not a CLI bug.**
   Running `opencode plugin list` was a misuse of the command; it added
   `"list"` as a plugin name to the project config. The CLI's
   `opencode plugin <pkg>` verb is for installing, not listing. No upstream
   issue warranted.
